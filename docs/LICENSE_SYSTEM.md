# نظام الترخيص — التصميم التقني

> Phase 15B · v2.0 · نظام ترخيص يعمل **دون إنترنت بالكامل**

## 1. المبدأ الأساسي

النظام مبنيّ على **التشفير غير المتماثل (Asymmetric Cryptography)**:

| | المفتاح الخاص (Private) | المفتاح العام (Public) |
|---|---|---|
| الوظيفة | **يوقّع** التراخيص | **يتحقّق** من التوقيع |
| المكان | `tools/license-generator/keys/` فقط | مدمج في التطبيق |
| هل يُشحن للعميل؟ | **لا — أبداً** | نعم |

النتيجة: التطبيق يستطيع أن يتحقّق من أن الترخيص صادر منك، لكنه **لا يستطيع أن يصدر
ترخيصاً**. لا يوجد في الشيفرة المشحونة أي مسار يُنتج ترخيصاً، لأن المفتاح الخاص ليس فيها.

لا يوجد **أي** خادم، ولا API، ولا سحابة، ولا اتصال بالإنترنت في أي خطوة من خطوات
التفعيل أو التحقق.

## 2. المعمارية — ثلاث وحدات منفصلة

```
packages/license-sdk/          ← منطق مشترك (بلا مفاتيح)
  ├── types.ts                  العقود والأنواع والحدود
  ├── crypto.ts                 canonicalize / sign / verify / encode / decode
  ├── fingerprint.ts            بصمة الجهاز (5 مكوّنات)
  └── validate.ts               قواعد صلاحية الترخيص

tools/license-generator/       ← أداة المطوّر فقط (لا تُشحن)
  ├── src/cli.ts                keygen / issue / inspect
  ├── keys/                     ⚠ المفتاح الخاص — متجاهَل في Git
  └── issued/                   التراخيص الصادرة — متجاهَل في Git

apps/desktop/src/main/license/ ← داخل المنتج المشحون
  ├── public-key.ts             المفتاح العام فقط
  └── license-service.ts        تقييم/استيراد/سماح/سجلّ
```

**لماذا مولّد التراخيص مشروع منفصل تماماً؟** لأن الفصل الفيزيائي أقوى من أي حماية
برمجية: ملفّات المولّد ليست جزءاً من مخرجات البناء، فلا يمكن أن تتسرّب مع الحزمة
حتى لو أخطأ أحد في إعدادات التغليف. وهذا هو السبب أيضاً في أن `keys/` و`issued/`
متجاهلتان في Git — يجب ألّا يدخل المفتاح الخاص إلى المستودع أبداً.

## 3. بصمة الجهاز (Machine Fingerprint)

### المصادر الخمسة

| المكوّن | المصدر | ثباته |
|---|---|---|
| `machineGuid` | `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` | يتغيّر بإعادة تثبيت ويندوز |
| `systemUuid` | `Win32_ComputerSystemProduct.UUID` | ثابت مع اللوحة |
| `baseboardSerial` | `Win32_BaseBoard.SerialNumber` | ثابت مع اللوحة |
| `cpuId` | `Win32_Processor.ProcessorId` | يتغيّر بتبديل المعالج |
| `diskSerial` | `Win32_DiskDrive.SerialNumber` (أوّل قرص) | يتغيّر بتبديل القرص |

كل مكوّن يُهشَّم **منفصلاً** بـ SHA-256 مع بادئة اسمه:

```
hash(component) = SHA256("<name>:<VALUE_UPPERCASE>")
```

ثم يُشتقّ الهاش الكلّي من المكوّنات مرتّبة أبجدياً، ومنه معرّف العرض:

```
LAU-143D-04DB-8E71     ← أول 12 خانة hex من الهاش الكلّي
```

**لا تُخزَّن ولا تُرسل أي قيمة عتاد خام.** الترخيص وطلب التفعيل يحتويان الهاشات فقط.

### لماذا كل مكوّن على حدة؟

لأن هذا يسمح بـ **المطابقة بالنقاط**: نقارن مكوّناً بمكوّن ونعدّ المتطابق.

### المطابقة بالنقاط — 3 من 5

```
score = عدد المكوّنات المتطابقة (غير الفارغة)
الترخيص يُقبل إذا score >= 3
```

| السيناريو | النتيجة |
|---|---|
| نفس الجهاز تماماً | 5/5 ✅ |
| استُبدل القرص الصلب | 4/5 ✅ |
| استُبدل القرص + المعالج | 3/5 ✅ |
| استُبدلت اللوحة الأم + القرص + المعالج | 2/5 ❌ |
| جهاز مختلف تماماً | 0/5 ❌ |

**السبب:** لو ربطنا الترخيص بمكوّن واحد، فإن تبديل قرص صلب معطوب يوم الجمعة يُوقف
مغسلة العميل. ولو تساهلنا أكثر من ذلك، لأصبح نسخ الترخيص لجهاز آخر ممكناً. عتبة
3/5 توازن بين الاثنين: الصيانة العادية لا تكسر الترخيص، وجهاز جديد لا يقبله.

## 4. صيغة ملفّ الترخيص

```json
{
  "payload": {
    "schema": 1,
    "licenseId": "0599e85c-…",
    "customerName": "مغسلة النور",
    "companyName": "Al-Noor Laundry",
    "type": "professional",
    "expiryDate": "2027-08-01T…" ,   // null = ترخيص دائم
    "issueDate": "2026-08-01T…",
    "maxUsers": 5, "maxDevices": 3, "maxBranches": -1,   // -1 = غير محدود
    "features": ["backup", "offline_sync", "multi_branch", "reports_advanced"],
    "minAppVersion": "2.0",
    "machine": { "machineId": "LAU-…", "fullHash": "…", "components": { … } }
  },
  "signature": "<512 بايت RSA بـ base64>",
  "algorithm": "RSA-SHA256"
}
```

يُخزَّن الملفّ مُرمَّزاً بـ base64 داخل غلاف نصّي:

```
-----BEGIN LAUNDRY ERP LICENSE-----
eyJwYXlsb2FkIjp7InNjaGVtYSI6MSwibGljZW5zZUlkIjoi…
-----END LAUNDRY ERP LICENSE-----
```

> ⚠️ **الترميز ليس تشفيراً.** أي شخص يستطيع قراءة محتوى الترخيص — وهذا مقصود:
> السرّية ليست هدفاً، **عدم القابلية للتزوير** هو الهدف. الغلاف موجود ليَعبُر
> الملفّ عبر البريد والنسخ واللصق دون تلف.

### التوقيع — لماذا `canonicalize`؟

`JSON.stringify` لا يضمن ترتيب المفاتيح، وأي اختلاف بايت واحد يُبطل التوقيع. لذلك
تُسلسَل الحمولة قبل التوقيع والتحقّق بدالة `canonicalize()` التي ترتّب مفاتيح كل
كائن أبجدياً بشكل تعاودي. بهذا يكون التوقيع **حتمياً** ومستقرّاً عبر الإصدارات.

## 5. ترتيب فحوص التحقق

الترتيب مقصود ولا يجوز تغييره:

```
1. كشف إرجاع ساعة النظام   → clock_tampered
2. التحقّق من التوقيع        → signature_invalid   ← قبل قراءة أي حقل
3. سلامة البنية             → malformed
4. مطابقة الجهاز (3/5)      → machine_mismatch
5. تاريخ الإصدار            → not_yet_valid
6. تاريخ الانتهاء           → expired
7. الحدّ الأدنى للإصدار      → version_unsupported
```

**التوقيع يُفحص أولاً لأننا لا نثق بأي حقل قبل إثبات أنه لم يُعدَّل.** لو فحصنا
تاريخ الانتهاء قبل التوقيع، لكنّا نقرأ رقماً كتبه المهاجم.

### كشف إرجاع الساعة

يُخزَّن `license.lastSeen` في **قاعدة SQLite المشفّرة** ويتقدّم للأمام فقط. إذا
أصبحت ساعة النظام أقدم منه بأكثر من يوم، فهذه محاولة تمديد صلاحية ⇒ `clock_tampered`.

## 6. سياسة الفشل — فترة سماح ثم تقييد

القرار: **لا نُوقف مغسلة عن العمل فجأة.**

```
ترخيص صالح
   └─ كل شيء يعمل

ترخيص غير صالح (منتهٍ / جهاز غير مطابق / مفقود)
   ├─ أول 14 يوماً  → النظام يعمل كاملاً + تحذير واضح في الواجهة
   └─ بعد 14 يوماً  → البيع موقوف، والقراءة والتصدير والنسخ الاحتياطي تبقى متاحة
```

بيانات العميل **لا تُحجب أبداً** مهما كانت حالة الترخيص. `license.graceStartedAt`
يُخزَّن هو الآخر في القاعدة المشفّرة، ويُمسح فور نجاح أي تحقّق.

## 7. أنواع التراخيص

| النوع | المستخدمون | الفروع | الأجهزة | المزايا |
|---|---|---|---|---|
| `trial` | 2 | 1 | 1 | أساسية |
| `starter` | 3 | 1 | 2 | + النسخ الاحتياطي |

`-1` تعني **غير محدود**. الحدود مُوقَّعة داخل الحمولة، فتعديلها يُبطل التوقيع.

## 8. حدود النظام — ما الذي لا يحميه

من الأمانة توضيح ما لا يفعله هذا التصميم:

1. **لا يمنع الهندسة العكسية.** من يستطيع تعديل ملفّات التطبيق يستطيع استبدال
   المفتاح العام المدمج بمفتاحه وإصدار تراخيصه. هذا صحيح في **كل** نظام ترخيص
   محلّي بلا استثناء، تجارياً كان أو مفتوح المصدر.
2. **لا يمنع النسخ الاحتياطي للقرص كاملاً** إلى جهاز مطابق افتراضياً (VM Clone).
3. **لا يحصي التثبيتات مركزياً** — لا يوجد خادم يعدّ. `maxDevices` معلومة تعاقدية
   تفرضها بإصدار عدد التراخيص المتّفق عليه، لا تقنية.

ما يمنعه فعلياً وبقوّة رياضية: **تزوير ترخيص، أو تعديل ترخيص قائم، أو استخدام ترخيص
عميل على جهاز عميل آخر.** كسر RSA-4096 غير عملي.

الحماية الحقيقية ضد التعديل هي **توقيع الملفّ التنفيذي بشهادة OV/EV** — عندها يفقد
أي ملفّ مُعدَّل توقيعه ويحذّر ويندوز منه. (راجع `docs/CODE_SIGNING.md`.)
